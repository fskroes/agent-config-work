# Large task protocol

Invoke this skill again after every compaction: compaction keeps only the first part of an invoked skill's text, and the loop below has to survive to the end of the task. Two rules hold at every size, not only here: the critic never sees the builder's reasoning, so a critic is never a fork of the lead's conversation (an Agent-tool fork inherits all of it; the `/critic` skill's `context: fork` is different, it starts the reviewer in an empty context); and the one cold critic pass a medium task gets is `/critic <deliverable> <reference>`.

This skill is a permanent, explicit opt-in to multi-agent orchestration (ultracode / the Workflow tool) for every task triaged **large**, and for **medium** tasks that split into truly independent units. Small tasks never fan out. The triage block (see "Task sizing" in AGENTS.md) is where the call is made and announced; when this loop runs, say so out loud, and when it is skipped, say that too and why.

**Step 0: name the reference before building.** The critic is only as good as what it judges against. Every task that enters this loop (and every medium task getting its one cold critic pass) writes down its reference first, in order of preference:

1. **The real thing** (copy/parity work): the actual product being matched. Blind side-by-side.
2. **Best-in-class analog** (new work): the best existing example of this kind of deliverable, named explicitly. Judged side-by-side even though we are not copying it. For UI work, the screenshots of two competitors (see "UI climb").
3. **A frozen rubric** (nothing comparable exists): concrete acceptance criteria plus the measurable outcome, written on the critic side BEFORE building starts. Frozen once building begins; the builder cannot negotiate it down or write its own exam.

Next to the reference, write the budget: the number of critic and verifier runs this task may spend (see "Budget and log" below).

No reference, no build. If you can't write down what "wowed" means for this task, that's a Confusion Protocol stop.

**The loop, for every task triaged large:**

1. **Decompose and fan out.** Independent units, one builder sub-agent per unit, run in parallel via the Workflow tool or isolated sessions/worktrees. Serial work on parallelizable units is wasted wall-clock. Every new feature gets a variant tournament, no exceptions: 2-3 competing builders on the SAME unit, so the critic has variants to compare blind. A small codebase or a session USD cap does not cancel the tournament. If the cap cannot fit 2 builders plus the critic budget, say so in the triage block and stop. Do not build solo. In the large-task eval on 2026-11-20, 3 of 12 leads built solo and gave as reason the run's USD 15 cap and the small size of the 40-line app. Because tournament builders write the same files at the same time, they are launched with `isolation: "worktree"`, see "Branching", where sharing one working tree between parallel writers is exactly the failure being designed out. **An `isolation: "worktree"` builder starts on the repo's default branch, not on the lead's task branch**, so it does not see a foundation commit the lead made first. The first line of every builder prompt is therefore `git switch -C <unit-branch> <task-branch>`, then `git merge-base --is-ancestor <foundation commit> HEAD`. The `git switch -C` line comes before any role line ("You are builder X"): the role goes under it. In the same eval, 3 of the 12 leads that fanned out put "You are builder X in a variant tournament" first. In one repo on 2026-10-21, seven of ten builders found the old base on their own; three never started and were stopped after three hours. A worktree does not share the RAM: every builder runs its tests and builds through `python3 ~/.claude/scripts/capped_run.py -- <command>` ("Tests and evals"), which reserves each run's `--mem-gb` (default 6) from a machine memory budget (0.75 x RAM): runs that fit start together, a run that does not fit waits. Builders queue there; they never stop the other builder's run, and a long wait is a reason to run a narrower `--filter` or a lower `--mem-gb` that the run really fits in, not to work around the budget. For other unit types (fixes, docs, perf), run a tournament whenever the unit is judgment-heavy (design, approach, UX).
   **A worktree does not isolate the scratchpad either.** Every sub-agent of a session gets the same scratchpad folder, so two builders that both write `scratchpad/patch_cli.py` overwrite each other's script, and one runs the other's code. The builder prompt names a scratch subfolder of its own: `scratchpad/<unit>-<variant>/`, never the scratchpad root. In one repo on 2026-10-28, builder B ran builder A's patch script, got A's code in its tree, and spent a round restoring it.
   **A builder never waits more than 270 s in one call.** Sub-agent requests use the 5 minute prompt cache. A wait longer than that lets it expire, and the next request writes the builder's whole context again at 12x the price of reading it. The builder prompt says: start a long build or test run with `run_in_background: true`, then poll its log in calls of at most 270 s (`timeout: 270000`), for example `for i in $(seq 26); do grep -qs DONE build.log && break; sleep 10; done`. Each poll then reads the cache instead of writing it. In an iOS app repo in 2026-W43, three iOS e2e builders polled `xcodebuild` in 600 s calls: 206 cache misses, 107M tokens written again, about $250 of the week's $315 loss. `guard.py` rule `subagent-wait` denies a longer foreground wait in a sub-agent (an `until`/`while` loop, `sleep`, `wait`, `tail -f`). It does not deny a long build that runs in the foreground: 83% of sub-agent calls with a long timeout end in under 270 s, so that would mostly cost retries. Such a build still costs one cache miss, so start it in the background too.
   **Stacked PRs land on `main` only when the bottom one merges first.** When units ship as stacked PRs (PR 2 has PR 1's branch as its base), GitHub moves PR 2 to `main` only if PR 1's branch is deleted when PR 1 merges. If PR 2 is merged while its base is still PR 1's branch, it lands on that branch and never reaches `main`. So the report that hands stacked PRs to Fernando says: merge them one at a time, bottom first, and check that the next one's base reads `main` before you merge it. After any merge of a stacked PR, the lead runs `git merge-base --is-ancestor <its head> origin/main`; if that fails, it rebases the rest onto `origin/main`, retargets the open PR to `main`, and says so. In one repo on 2026-10-28, #8 merged into #7's branch 14 seconds after #7 merged, and the verify skill missed `main` until #9 carried it.
   **The lead keeps working while sub-agents run.** It does not sit idle and wait.
   - What the guide says: Anthropic's Fable 5.1 guide (section "Let the lead agent keep working while subagents run") reports that on coding tasks, letting the lead continue "lowers average time to completion at similar quality, token usage, and cost".
   - How it works here: the Agent and Workflow tools run in the background and send a notification when each one finishes. The lead has nothing to wait on.
   - Our rule, not the guide's: apply it to non-code units too. While waiting, check each result as it arrives, send follow-ups to a sub-agent with SendMessage, and prepare the next step. Keep working, but not in a tree a critic or verifier is reading (step 3).
2. **Builder never grades its own work.** Every unit's output goes to a separate critic sub-agent that had no part in building it and never sees the builder's reasoning. Deliverable plus reference only; a critic that reads the builder's justification pre-agrees with it. The critic prompt never holds a target score, the round number, the rounds left or the verdict the lead hopes for: a judge that knows the target moves toward it. Self-review does not count as review. `/critic` runs in a fresh context by construction; a fork does not, so never use one as a critic.
   **The extra critic slot: a second critic with other blind spots.** A Claude critic shares the Claude builder's blind spots. The slot adds one critic that shares fewer of them. It is opt-in, and it is measured: the log in "Budget and log" decides whether the slot is kept, swapped or dropped.
   - **The flag.** `git config agent.extraCritic` (when it is not set, the old name `git config claude.extraCritic`) names what fills the slot: `codex` (the Codex CLI, a different model family), `claude` (the `reviewer` agent on a Claude model the builder did not run on) or `both` (the two side by side on the same task, the A/B in "Budget and log"). Unset means no extra critic. `git config --global` sets it for all repos. The older `git config agent.codexCritic on` (or `claude.codexCritic on`) means `codex`. Fernando sets these flags; never set one yourself. Since 2026-10-18 the global value is `claude`: Codex is not a critic. On 2026-11-08 the last exception, the screenshot-only Codex critic of a UI round, ended. No Codex critic runs anywhere, code or UI. When a repo still says `codex` or `both`, run only the `claude` critic, and say so in the report.
   - **When it runs.** On code units. A UI round has its own second Claude critic (see "UI climb", rule 5).
   - **How many.** Large loop: one extra critic per round; the Claude critics stay as they are. Medium task: the extra critic runs next to the one Claude cold critic, not in place of it.
   - **`claude`: a second Claude model.** Launch the `Agent` tool with `subagent_type: "reviewer"`, `model: "opus"`, `effort: "medium"`, and as prompt the body of `~/.claude/skills/critic/SKILL.md` with the deliverable and the reference filled in. Always Opus on medium effort, also when the builder runs Opus: Fernando set this on 2026-10-18, so it is the explicit instruction the `effort` parameter needs. The cold critic stays the `reviewer` default (Sonnet). Name the model and effort in the log line's `--note` (`opus medium`). Never a fork: a fork inherits the lead's reasoning. Nothing leaves the machine beyond a normal Claude Code call, so no secrets check.
   - **Its findings.** The same filter as every critic, step 3: confirmed against the source or dropped.
   - **Visible.** The final report of every task that ran the extra critic names which kind ran, and says so when a repo flag of `codex` or `both` was reduced to `claude`.
   - **LLM access.** That rule covers LLM calls inside the software we build, not tools used while building it. No conflict.
3. **The critic is harsh by default; its job is to reject.** Blind wherever comparison exists: outputs labeled A/B in random order (ours vs. the reference, or variant vs. variant) so the critic doesn't know which is ours. The verdict must be concrete: which is better and exactly why. "Pretty good" is a FAIL. "Acceptable" is a FAIL. The bar is harsh on what matters: every finding carries a severity (high, medium or low, defined in `/critic`), and a round with no confirmed high and no confirmed medium finding is a PASS. Low findings (hardening, docs, input the system never produces) are follow-ups for the final report and never cost a round. A critic that keeps finding new edge-case classes in a correct unit is finding low items, and the severity rule is what stops that loop.
   **Verify against the live thing, not the diff.** The diff is the builder's account of the change; the running program is the source. In a repo that has a `verify-<app>` skill (under `.claude/skills/` of the repo, see "Solo merge needs a passing verify run" in AGENTS.md), the critic runs it on the deliverable and pastes its summary line in the verdict. A verify FAIL is a FAIL verdict, and in such a repo a verdict written from the diff alone is not a verdict. In a repo with a runtime (something that boots, serves or renders) and no verify skill, the critic uses the deliverable by hand (runs it, calls it, opens it) and says what it did.
   In a repo with no runtime (scripts, hooks, markdown) the tests against a throwaway environment and the docs critic following the text cold are the live check. Verifiers read; a verifier that wants to fix something is a builder and gets its own worktree.
   **The lead does not write in the tree under review.** While a critic or verifier round runs on a tree, the lead does not write in that tree. A fix waits for the verdict, or is built in its own worktree and merged after. A critic notification that says the agent is "waiting on its own background work" is interim, not the verdict: wait for the final one. A critic sub-agent shares the lead's worktree ("Branching"), so an edit or a commit there changes what the critic reads during its run. In one task (2026-10-21) the lead committed a fix while the system-round critic ran on the same checkout: a test failed on the half-edited tree, and the round was logged FAIL and run again, one critic run of the budget lost.
   **Assert or drop, never hedge.** Every finding in a verdict is confirmed at a place the critic looked at: a file and line, a command and its output, a screenshot. A finding the critic could not confirm goes under "Could not check" with what would settle it, never into the findings with "may", "might" or "possibly". The lead applies the same filter to every critic's output, Claude, the extra slot or a verifier: confirm each finding against the source, fix the confirmed ones, drop the rest and say how many were dropped. A hedged finding costs more than a missed one: the builder spends a round on a non-bug and the real finding hides next to it. The wording comes from Anthropic's "Building effective agent automations" (8 October 2026): "never hedge an item's status: assert it or drop it."
4. **Loop until pass, at most 3 rounds per unit.** Builder revises against the critic's named findings. A fresh critic judges cold each round. A pass requires the critic's explicit verdict, never the builder's claim.
   - **Round 1** is a full harsh critic, plus `scripts/verify` where the repo has one.
   - **Rounds 2 and later are regression rounds** (see `/critic`, "Regression round"). The lead puts the previous round's confirmed findings, with their evidence, into the prompt, never the builder's reasoning. The critic checks that each one is fixed (running the repro where one exists), looks for regressions in the files the fix changed, and adds a new finding only if it is high and its repro ran. A fresh full review every round is what let a correct unit meet a new edge-case class each time and never pass.
   - **A unit exits on PASS.** Its low items become follow-ups in the final report.
   - **Cap: 3 rounds per unit.** At the cap the unit stops and ships with its open items reported as concerns (DONE_WITH_CONCERNS). If an open item is high, the lead asks Fernando before the unit ships. There is no fourth round.
   - **System round, after the units merge.** One required critic round runs on the integrated deliverable. It drives the running system (the verify script, the CLI, a real fixture), not the diff. It is a full round, not a regression round, and it logs with `--unit system`. Bugs at unit seams and in the running system are the most valuable ones, and no unit critic sees them. Its confirmed high and medium findings go back to the unit that owns the code for one fix round, followed by a regression round on that fix. That fix round counts toward the cap of that unit. If that unit is already at its cap, the lead fixes the finding itself and reruns the system round, which logs as `--unit system`. If the system round is itself at its cap of 3, or the open item is high, the lead asks Fernando.
   - When the deliverable is not a diff (a URL, a running app, a design), the lead lists the changed paths in the critic's prompt, so the critic can tell what changed. A finding in code the deliverable did not change is a follow-up for the report (see "Scope" in AGENTS.md), not a reason for another round.
   - **Repeat filter:** from round 2 on, the lead compares each finding with the critiques of the earlier rounds in `/tmp/<task>/critique/`. A finding that was fixed and comes back without new evidence (a new file:line, a new failing command) is a repeat: drop it and log the count as `--repeats`. A finding that was fixed and is still broken is not a repeat; it stays. The critic has no memory, so this filter is the lead's job, never the critic's.
5. **Stall rule.** If 3 consecutive rounds of one unit produce no improvement on the critic's named criteria, stop that unit's loop and report it with the critic's last verdict, the evidence, and what's missing (asset, tool, or decision from Fernando). Since the cap is 3 rounds per unit, the stall rule can fire only on the last round of a unit; it decides whether the unit ships with concerns or goes to Fernando as BLOCKED. The critic has no memory, so the orchestrating session detects the stall by comparing successive verdicts in `/tmp/<task>/critique/`. Do not silently lower the bar to exit the loop.
   **Three rounds without a pass means the approach of that unit is wrong.** The cap counts per unit, not per task. Before every round, run `critic_log.py count --task <slug> --unit <unit> --budget <n> --round <the round about to start>` (see "Budget and log"); exit 1 means stop here, and step 4's cap rule applies. Why 3: after a 3-round cap, Anthropic's "Solving code review at Anthropic" saw the share of PRs that needed 5+ rounds fall from 8.9% to 1.5%. Here, in week 2026-W42, 58% of 19 looped tasks went past round 3; in build-engine-478e4683 the late unit rounds found hardening items, about 1.9 confirmed findings per run against about 4.3 for system runs. A report that asks Fernando to rethink the approach (a high open item at the cap, or a stalled unit) names the approach the builder took, the findings that came back or moved round after round (from `/tmp/<task>/critique/`), and one or two different approaches with what each changes. Fernando picks one, and that is a new loop with a new budget.
6. **Evidence or it didn't happen.** Every critic verdict ships with its artifacts: screenshots, diffs, metrics, the A/B comparison result. Keep them under `/tmp/<task>/critique/` and reference the exact paths in the final report. They stay in `/tmp`, never in the repo (Safety: no binaries committed).

**Budget and log.** Critic and verifier runs are the task's variable cost, so they are capped and counted. The cap follows the same article: cap what each run can spend, "start at three to five times the cost of a normal run, then tighten it as you see real numbers".

- **The budget** is a number of critic plus verifier runs per task, written in Step 0 next to the reference. The budget stays per task; the round cap is per unit. Default for critic runs: about 2 per unit (round 1, plus one regression round) plus about 30% of the total kept for system and cross-unit runs, so `ceil(2 * units / 0.7)`: 20 for 7 units. Verify runs are counted separately: add one per unit and one for the system round in a repo that has the skill. When the extra critic flag is on, add one extra critic run per round that runs. The 2 per unit is an average. A unit that needs its third round takes the share of a unit that passed at round 1. `git config agent.criticBudget <n>` (or the old name `claude.criticBudget`) replaces the default for a repo; Fernando sets it, never raise it yourself. A medium task writes its budget in Step 0 too (Step 0 covers every task that gets a critic pass): one round there is the cold critic, plus a verify run where the skill exists, plus the extra critic when the flag is on. When the count reaches the budget, `count` exits 1: the loop stops and reports BLOCKED with the last verdict, the same as the stall rule.
- **The log.** After every critic or verifier run, append one line; before every run, check the count against the budget (exit 1 means spent):

  ```bash
  python3 ~/.claude/agent-metrics/critic_log.py add --task <slug> --kind claude|claude-alt|codex|verify \
      --verdict PASS|FAIL --findings N --confirmed N --unique N --round R --repeats N --followups N \
      --unit <unit> --severity-high N --severity-medium N --severity-low N
  python3 ~/.claude/agent-metrics/critic_log.py count --task <slug> --unit <unit> --budget <n> --round <next round>
  ```

  `count` also enforces the round cap per (task, unit): it exits 1 when the next round, or a round already logged for that unit, is past 3, and step 5 applies. Name the unit in every `add` and `count` of a multi-unit task. The system round uses `--unit system`. A single-unit task may leave `--unit` out. `--severity-*` are the confirmed findings of the run by severity (their sum is at most `confirmed`); the low ones are the follow-ups. Never pass a higher `--max-rounds` unless Fernando says so. `repeats` is what the repeat filter dropped (so `confirmed + repeats <= findings`), `followups` is the critic's "Follow-ups" count.

  `<slug>` is the branch slug from the triage block. `--kind` is `claude` for the cold critic, `claude-alt` for the extra slot (the `claude` flag value logs as `claude-alt`, so the two Claude critics stay apart in the tally; `codex` stays valid only for old log rows), `verify` for a verify run. `findings` is what the critic reported, `confirmed` what survived the assert-or-drop filter, `unique` the confirmed findings no other critic of the same round reported. The lead judges those three numbers; the script only counts them. The log is per machine, under `~/.claude/agent-metrics/history/critics.jsonl`.
- **The decision rule for the extra slot.** The Codex A/B on code units ended on 2026-10-18 with `claude` as the choice (the A/B procedure is in git history). The screenshot-only Codex critic of a UI round, approved on 2026-11-07, ended on 2026-11-08 (see "UI climb", rule 5). When `claude-alt` has 20 runs and its `unique_per_run` is under 0.1, the slot does not pay for its runs: tell Fernando, who unsets the flag and logs it in `changes.md`. `weekly.sh` writes `history/<week>-critics.tsv` from the log, one row per kind.

**The critic per work type** (the pattern is constant, the weapon changes):

- **Copy/parity:** real reference, blind side-by-side, visual and behavioral.
- **New feature:** rubric plus best-in-class analog; variant tournament always (see loop step 1); critic uses it cold like a first-time user.
- **Bug fix:** the reference is the repro. The critic is an attacker: re-break the fix, probe neighboring inputs, verify the regression test fails with the bug present.
- **Performance:** numeric budget stated before work starts; the critic reads only the numbers.
- **Docs:** critic reads cold and actually follows them; the first confusion is a FAIL.
- **Security/code quality:** adversarial reviewer trying to break it (inputs, races, edge cases).
- **UI and visual work:** see "UI climb" below.

**UI climb: the rules for UI and visual work.** A UI unit is one whose deliverable is judged by how it looks: a screen, a layout, a theme, a component's style. A model that judges one design with nothing beside it is too easy on it. In Theo's T3 Code run (video "Agents Sucked At UI (Until Today)", 2026), the same PR got 9/10 alone and 7.4/10 next to Claude Code and Codex. These rules add to the loop above. The round cap, the budget and the log stay the same.

2. **The reference is the competitors.** The Step 0 reference is screenshots of the two best apps of the same kind, in the same state as the deliverable (same screen, same data, same theme), plus the screenshot of our version before the change. Name the apps. Our old version alone is not a reference.
3. **A control pair, judged every round.** In round 1, pick two of the reference screenshots as the control pair. Do not change these files until the unit ends. Every critic prompt holds the control pair as one more blind A/B, mixed in with the real comparison, and does not say which pair is the control. If the control verdict differs from the round 1 verdict, the judge drifted: the lead discards the round, logs it with `--note control-flip`, and runs it once more with the same `--round`. The rerun counts against the budget. In the video, the unchanged Claude Code screenshots went from 8.3 to 9.1 over the rounds.
4. **The critic never sees the target** (the rule in step 2 holds here too). In the video, the scores landed on exactly 9.5 after the prompt asked for 9.5.
5. **A second Claude critic.** Every UI round adds one second Claude critic next to the cold critic, from the extra slot of step 2: the `reviewer` agent with `model: "opus"` and `effort: "medium"`, never a fork. Its prompt holds the screenshots, the /critic rubric and the blind A/B pairs, and no target. It gets screenshots only, never code. Log it as `--kind claude-alt` with `--note opus medium`. No Codex critic runs in a UI round: the decision of 2026-11-08 (no Codex, Claude only) reverses the 2026-11-07 approval of a screenshot-only Codex critic (PR #110). The Codex login had also expired ("refresh token was already used"), so the rule failed in practice. Nothing leaves the machine beyond a normal Claude Code call, so no secrets check, the same as in step 2. In the video, the judge that disagreed (7.5 when the others gave 9) showed where the remaining gain was.
6. **Fernando's taste gate.** After the first PASS of a UI unit, stop before the unit ships. Show Fernando the before and after screenshots side by side, with a note on each change (an Artifact page or one HTML file), and ask for one sentence of direction. That sentence goes into the frozen rubric. If it asks for a change, the unit gets one more round, inside its cap. In the video, the climb drifted to grayscale until one human line ("restore some color") fixed it.

**Solo (no fan-out) is the rule for:** small tasks, most medium tasks, conversational answers, and reading/investigation that fits in one context. Medium bug fixes still get the one cold critic pass from "Task sizing" (an attacker on the repro), just not the tournament. When in doubt between medium and large, triage says pick medium; when a large task is in doubt about how to split, fan out.
